# Семейный бюджет

Приложение вместо гугл-таблицы «Траты на 2024». Планирование от получки к получке:
обязательные траты, необязательные, приходы, план против факта, аналитика за три года.
Статический сайт на GitHub Pages, данные — JSON в этом же репозитории.

## Что где

```
public/data/       данные: paychecks, entries, templates, salary, calendar, categories, groups, meta
tools/migrate.py   разовый перенос исходной таблицы в public/data
src/workdays.ts    производственный календарь и даты получек
src/salary.ts      оклад, индексация, расчёт получки по рабочим дням
src/plan.ts        генерация получек вперёд и перенос правок на следующие
src/calc.ts        итоги получки и месяца, долговая нагрузка, план против факта
src/store.tsx      загрузка, черновик в localStorage, история «Назад», публикация
src/github.ts      запись данных в репозиторий одним коммитом
src/components/Sortable.tsx   перетаскивание строк пальцем и мышью
src/views/Ledger.tsx          «Журнал»: месяцы рядом, свод по категориям, все строки
src/views/Categories.tsx      разбор категорий: что куда попало, слияние, архив
src/views/Workdays.tsx        таблица рабочих дней на текущий и будущие месяцы
```

## Модель данных

| Сущность | Что это |
|---|---|
| `paychecks` | получка: дата, ручная сумма вместо расчёта (`salaryOverride`) и фактическая (`salaryFact`) |
| `entries` | строка внутри получки: `kind` = `required` / `optional` / `income`, `plan`, `fact` |
| `categories` | подкатегории; `archived: true` убирает из выбора, историю не трогает |
| `groups` | крупные категории (Долги, Жильё, Еда…), `order` задаёт порядок в списках |
| `templates` | база будущих получек: регулярные траты (в каждую 1-ю или 2-ю получку) и ежегодные события |
| `salary` | оклад по датам и правило индексации |
| `calendar` | поправки к производственному календарю и таблица рабочих дней `months` |

Приход — отдельный тип строки, а не отрицательная трата: в исходной таблице отпускные
и возвраты стояли минусом среди расходов, из-за чего доход был занижен.

Категории трёхуровневые: **крупная категория** (`groups`, их мало и они не меняются) →
**подкатегория** (`categories`, отвечает «что это за трата») → **название строки**
(`entries[].title`, свободный текст-деталь). Названия категорию не задают: одна
подкатегория собирает сколько угодно разных названий. Что во что попало, видно на экране
«Настройки» → «Категории»: у каждой подкатегории видно все названия, которые в неё попали,
сколько строк и денег, когда последний раз. Там же переименование, перенос в другую крупную
категорию, слияние двух подкатегорий (строки и шаблоны переезжают) и архив — он убирает
подкатегорию из выбора, историю не трогает. Что с чем сливать и что прятать, приложение
не решает и не предлагает: это ручная работа хозяина данных.

## Как считается зарплата

Получка 21-го числа — за рабочие дни с 1 по 15 этого месяца, получка 6-го — за вторую
половину предыдущего. Сумма = оклад ÷ рабочих дней месяца × рабочих дней периода.
Оклад берётся из `salary.json` на первый день периода; индексация поднимает его
с первого числа заданного месяца, поэтому первой её застаёт получка 21-го.

Праздники фиксированные, переносы правило выводит само («праздник на выходном сдвигает
ближайший рабочий день»). На 77 реальных получках оно ошиблось дважды, оба раза в конце
декабря — такие случаи лежат в `calendar.json`. Любую получку можно переопределить руками.

Рабочие дни можно не доверять расчёту, а вбить: «План» → «Рабочие дни», по месяцу начисления —
норма месяца, дни 1–15 (уезжают в получку 21-го) и дни 16–конец (в получку 6-го следующего).
Вбитое число всегда сильнее календаря, пустое поле — считаем сами. Показываются только текущий
и будущие месяцы: у прошлых получек сумма записана в `salaryOverride`, и правка дней их не задевает.

## Как работает план вперёд

Экран «План» продлевает график до выбранного года: создаёт недостающие получки и наполняет
их строками из `templates`. Уже существующие получки не трогает никогда.
Сейчас расписано по конец 2027 года — дальше досчитывается кнопкой «Продлить».

Правка строки в конкретной получке спрашивает, перенести ли её на все следующие получки
того же типа. «Только эта» — если ты просто подвинул трату между получками месяца.
«И дальше» — обновляет все будущие получки этого типа и саму базу, чтобы правка попала
и в получки, которых ещё нет. Прошлое не меняется ни в каком случае.

Правка самой базы (регулярная трата или ежегодное событие) спрашивает то же самое заранее —
переключателем «Куда попадают правки базы»:

| Вариант | Что делает |
|---|---|
| С текущей | задевает и ту получку, которую ты сейчас живёшь |
| Со следующей | текущая остаётся как есть — обычный случай: платёж изменился со следующего раза |
| Только в новых | уже расписанные получки не трогаем совсем |

Переименование кредита не означает, что кредит закрыт: строка находится в получках по старому
названию и переименовывается, сумма и факт остаются. Там, где факт уже проставлен, сумма не
переписывается никогда. Одноимённые траты разных получек («Ипотека» в 1-ю и во 2-ю) —
разные шаблоны и друг друга не задевают.

Правок в одной получке может быть сразу несколько: каждая встаёт в очередь и спрашивается
отдельно — «Только здесь» / «И дальше» разом или по одной. Ничего не ответил — все остаются
только в этой получке.

Строки внутри получки и строки базы переставляются перетаскиванием за ручку ⠿ (палец и мышь,
без HTML5 drag — он не работает на айфоне). Строку целиком можно перекинуть в соседнюю
получку: «⋯» у строки → «Перенести в другую получку». Там же категория строки и удаление.

Любое действие отменяется кнопкой «↶» в шапке (или ⌘/Ctrl+Z, ⇧⌘Z — вернуть). История
живёт до перезагрузки страницы, 40 шагов.

## Экраны

| Экран | Зачем |
|---|---|
| Сейчас | текущая получка: сколько свободно, что осталось оплатить |
| Получка | редактор одной получки со всеми строками |
| Журнал | все данные разом: месяцы рядом, свод «категория × месяц», плоский список строк с фильтрами |
| План | база регулярных трат, оклад, рабочие дни, продление плана |
| Аналитика | долговая нагрузка, кредиты, план против факта, итоги по годам |
| Настройки | подключение устройства, категории, данные |

## Разработка

```bash
npm install && npm run dev
```

В dev-режиме кнопка «Опубликовать» пишет прямо в `public/data` — токен не нужен.

## Деплой

Пуш в `main` запускает `.github/workflows/deploy.yml`: сборка и публикация на GitHub Pages.
В настройках репозитория: **Settings → Pages → Source: GitHub Actions**.

## Правка с телефона

Открыть сайт → «Настройки» → «Подключить это устройство» и пройти четыре шага мастера.
Владелец и репозиторий определяются из адреса сами. Ключ остаётся в `localStorage`
этого устройства. На телефоне жены его вводить не надо — без ключа приложение
работает как просмотр.

После «Опубликовать» правки уходят одним коммитом, сайт пересобирается за минуту-две.
До этого на своём устройстве видно свежую версию (черновик в `localStorage`), у остальных — прошлую.

## Повторная миграция

```bash
python3 tools/migrate.py "~/Downloads/Траты на 2024.xlsx"
```

Перезаписывает `public/data` целиком — все правки, сделанные в приложении, а также шаблоны,
оклад и продлённый план потеряются.
Нужна только если что-то в первом переносе окажется неверным.

## Приватность

Репозиторий публичный, поэтому `public/data` доступен всем, у кого есть ссылка.
`robots.txt` и `<meta name="robots">` закрывают сайт от поисковиков, но не от прямого доступа.
